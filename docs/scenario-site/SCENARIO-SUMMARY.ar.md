# دليل اختبار التدفقات — جرد هيونداي (من الكود)

مصدر الخطوات: `MobileApiController`، `NewPartRequestService`، `QuantityRequestService`، `PartService.RequestRecountAsync`، `MobileService`، `FinanceController`/`ExportService`، وقائمة القائمة في `_Layout.cshtml`.  
حسابات التجربة (بعد `Seed__Demo=true`): باسورد الكل `Test1234`.

| الدور | الهاتف | وين يشتغل |
|---|---|---|
| مسؤول رئيسي | 07790000000 | اللوحة |
| أحمد (موظف جرد) | 07790000001 | التطبيق فقط |
| أدمن المنصور | 07790000002 | اللوحة |
| مدير مخزن المنصور | 07790000003 | اللوحة |
| مدير القطع | 07790000004 | اللوحة · طلبات إضافة قطعة |
| محاسب المنصور | 07790000005 | اللوحة · مالية + قبول نهائي |
| مخزن قطع المنصور | رقم 9011 | التطبيق + اللوحة |
| مخزن مركبات المنصور | رقم 9012 | التطبيق + اللوحة |

لوحة التحكم: `http://127.0.0.1:5169` أو `https://hyundai.cloudapps.trade`  
API التطبيق: نفس الهوست تحت `/api/v1/...`

## 1) طلب إضافة قطعة للجرد

**موجود بالكود:** نعم — `POST /api/v1/new-part-requests` ثم لوحة `/NewParts`.

### مين يسوي شنو
1. **أحمد (تطبيق)** يرسل الطلب.
2. **مدير القطع 07790000004** يوافق أول مرة أو يرجع.
3. **محاسب المنصور 07790000005** يثبّت نهائياً → تنخلق قطعة بجلسة الجرد.
4. أحمد يشوف الحالة بتطبيقاته (`GET /api/v1/new-part-requests`).

### خطوات التطبيق (أحمد)
1. دخول `07790000001` / `Test1234`.
2. تأكد في جلسة حية (`GET /api/v1/sessions/current` ما يرجع null).
3. اختار مخزن المنصور التجريبي **9011** (خذ `warehouseId` من `/api/v1/me` مو الرقم 9011 نفسه).
4. امسح/أدخل رقم قطعة **غير موجودة** بالجلسة، مثال: `QA2630035506`.
5. املأ: وصف `جلدة باب تجريبية / Door seal`، كمية `2`، موقع `QA-Z-01`، GPS حقيقي (مو 0,0).
6. أرسل الطلب → API: `POST /api/v1/new-part-requests`.

**متوقع بالتطبيق فوراً:** رسالة نجاح، الحالة **«بانتظار مدير قطع الغيار»** (`PendingSparePartsManager`). **ما تنخلق قطعة** بعد (`InventoryPart`) لحد التثبيت.

### خطوات اللوحة
1. دخول مدير القطع → من القائمة **المخزون ← طلبات إضافة قطعة** (`/NewParts`).
2. افتح الطلب (رقم مرجعي مثل `0007`) → **تفاصيل**.
3. اضغط **موافقة** (`POST /NewParts/Approve/{id}`)  
   **متوقع:** فلاش «تمت الموافقة وتحويل الطلب للمالية»، الحالة **«بانتظار المالية»**.
4. خروج ودخول محاسب المنصور → نفس الصفحة `/NewParts` → **تثبيت / قبول نهائي** (`POST /NewParts/FinalApprove/{id}`)  
   **متوقع:** «تم التثبيت وإضافة القطعة للجرد»، الحالة **«مثبت»**.
5. روح **قطع الغيار** `/Parts` وابحث `QA2630035506`  
   **متوقع:** قطعة واحدة؛ كمية النظام `0`، المعدودة `2`، الموقع `QA-Z-01`، السعر `0` (الكود يثبّت `Price = 0`).

### رجوع الحالة للتطبيق
- بعد موافقة مدير القطع: **«بانتظار المالية»**.
- بعد تثبيت المحاسب: **«مثبت»** + سجل تدقيق (تم الإرسال → موافقة مدير قطع الغيار → تثبيت المالية).
- إذا المدير/المحاسب ضغط **إرجاع** مع سبب: **«رجع للموظف»**؛ أحمد يقدر **يلغي** فقط بهالحالة (`POST .../cancel`) → **«ملغي»**.
- تكرار نفس الرمز وطلب مفتوح: **409** «يوجد طلب إضافة مفتوح لهذه القطعة».

## 2) طلبات قطع الغيار

**بالكود:** ماكو قائمة اسمها حرفياً «طلبات قطع الغيار». اللي يخص **مدير قطع الغيار** هو منيو **«طلبات إضافة قطعة»** `/NewParts` (صلاحية `CanReviewNewPart`).

مدير القطع **ما يشوف** منيو قطع الغيار `/Parts` ولا طلبات التعديل `/Requests` (`Menu.Parts`/`Requests` ترفض SparePartsManager).

**اختبر بهذا:**
1. دخول `07790000004` → لازم تشوف **طلبات إضافة قطعة** فقط من قسم المخزون (مع الرئيسية).
2. فلتر الحالات: بانتظار مدير قطع الغيار / بانتظار المالية / مثبت / رجع للموظف.
3. أكو عينات جاهزة من الـ seed: `DEMO-NEW-1..4` بحالات مختلفة — ميّز طلباتك الجديدة بالوقت والرمز.
4. محاسب البصرة `07790000007` ما يشوف/يوافق طلبات المنصور (Scope حسب الفرع).

إذا تقصدون شاشة ثانية باسم «طلبات قطع الغيار» غير `/NewParts`: **غير موجود حالياً**.

## 3) فروقات المخزون (بعد العدّ)

**موجود:** نعم — تُحسب على `InventoryPart` بعد حفظ العد من التطبيق؛ العرض بقائمة **قطع الغيار** `/Parts` وتفاصيل القطعة، والتصدير، وصفحة المالية.

### خطوات
1. أحمد يعدّ القطع الخمسة (انظر جدول القسم 1 بالسيناريو الطويل) على مخزن 9011 مع GPS صحيح → `POST /api/v1/counts`.
2. مثال: `58101D3A01` كمية نظام `9` وعدّ `10` → فرق `+1`، سعر `85000` → قيمة فرق `85000`.
3. باللوحة: دخول أي دور يشوف القطع (مسؤول/أدمن/مدير مخزن/محاسب) → **قطع الغيار**.
4. ابحث الرقم → افتح **تفاصيل**: كمية النظام، المعدودة، الموقع، الموظف، الوقت، سجل التغييرات.

**متوقع:** نفس الأرقام بالتطبيق (`سجلي` / `GET /api/v1/history` و`parts`) وباللوحة.  
مجموع فروقات الخمسة المحددة بالوثيقة = **324,000 د.ع** (مو إجمالي كل الداشبورد لأن أكو مخازن ثانية).

**ملاحظة:** الفرق = `CountedQuantity - SystemQuantity` فقط إذا انعدّت القطعة؛ قبل العد الفرق فاضي.

## 4) المالية

**موجود:** نعم — منيو **«فروقات المخزون المالية»** `/Finance` (`FinanceController` + `ExportService.FinanceListAsync`). الأدوار: مسؤول رئيسي، سوبر، محاسب.

### خطوات
1. بعد ما تسوي عدّات (القسم 3) وحتى بعد تعديل كمية إن ردت، دخول محاسب المنصور `07790000005`.
2. افتح `/Finance`.
3. فلتر حسب الجلسة/الفرع/المخزن/نوع الفرق إن موجود، وابحث `58101D3A01`.
4. **متوقع بالجدول:**  
   System Quantity / Counted / Difference / Price / **Financial Difference**  
   حيث القيمة المالية = `(Counted - System) * Price` (تقريب منزلتين).  
   لـ `58101D3A01` بعد عد 10: فرق +1 × 85000 = **85000**.  
   بعد قبول تعديل كمية إلى 11 (القسم 5): فرق +2 × 85000 = **170000**.
5. زر **تصدير** ينزّل Excel `Financial-Variance` بنفس الأعمدة.

محاسب البصرة ما يشوف بيانات المنصور. مدير القطع **ما عنده** منيو المالية.

## 5) تعديل الكمية

**موجود:** نعم — تطبيق `POST /api/v1/qty-requests` + لوحة `/Requests` (وأيضاً من تفاصيل القطعة زر تحديث كمية).

### مسار الحالة (Labels.QtyMobile)
`بانتظار مدير المخزن` → (موافقة أولى) `بانتظار المالية` → (قبول نهائي) `مقبول`  
أو `مرفوض` مع سبب.

### خطوات
1. أحمد بعد عدّ `58101D3A01` بـ 10: من التطبيق أرسل تعديل كمية إلى **11**، سبب: `كارتون إضافي بعد المطابقة`.
2. **متوقع بالتطبيق:** «بانتظار مدير المخزن». باللوحة `/Requests`: طلب جديد، الكمية القديمة 10 والجديدة 11.
3. محاسب يحاول يوافق أول (`Approve`) → **يرفض الكود** («ليس لديك صلاحية» / مو `CanFirstApproveQty`).
4. مدير المخزن `07790000003` → `/Requests` → **قبول** (`Approve`)  
   **متوقع:** «تم قبول الطلب»، التطبيق يصير **«بانتظار المالية»**، الكمية المعدودة **تبقى 10**.
5. محاسب المنصور → **قبول نهائي** (`FinalApprove`)  
   **متوقع:** «تم القبول النهائي وتحديث الكمية»، القطعة `CountedQuantity = 11`، التطبيق **«مقبول»**، سجل تغيير «الكمية المحسوبة».
6. إعادة نفس القبول النهائي من تبويب ثاني: ما يتكرر؛ إذا SQLite مشغولة تظهر بالضبط:  
   **«قاعدة البيانات مشغولة، حدّث حالة الطلب قبل إعادة المحاولة»**.

طلب ثاني مفتوح لنفس القطعة: **409** «يوجد طلب تعديل قيد الانتظار لنفس القطعة».

## 6) إعادة الجرد (إعادة العد)

**موجود:** نعم — لوحة `Parts/Recount` + تطبيق `GET /api/v1/recounts` و`POST /api/v1/recounts/{id}/submit`.

### مين يقدر يطلب؟
مسؤول/سوبر/أدمن/مدير مخزن. **المحاسب ومدير القطع ممنوعين** («ليس لديك صلاحية»).

### خطوات
1. مدير المخزن → `/Parts` → تفاصيل `58101D3A01` → نموذج **إعادة عد** → اختار أحمد (أو نفس العداد) → إرسال.
2. **متوقع:** «تم إرسال طلب إعادة العد». طلب مكرر لنفس المستخدم وهو Pending → خطأ «يوجد طلب إعادة عد مفتوح لنفس المستخدم».
3. أحمد بالتطبيق يفتح مهام إعادة العد → يدخل كمية `10` وموقع `A-01` وGPS صحيح → إرسال.
4. **متوقع:** الطلب **مكتمل**؛ القطعة تتحدث عبر نفس مسار `CountAsync`؛ السجل يحافظ التاريخ.

## 7) تصحيح البيانات

**بالكود يوجد مساران واضحان، مو شاشة واحدة باسم «تصحيح البيانات»:**

### أ) تصحيح VIN (الأقرب لـ«تصحيح البيانات» للمركبات)
- تطبيق: `POST /api/v1/vin-corrections` بعد مسح VIN.
- لوحة: **طلبات تصحيح VIN** `/VinRequests` — فقط **أدمن الفرع** و**مدير المخزن** (`[Roles(Admin, WarehouseManager)]`).
- المحاسب **ما عنده** هالصفحة.
- موافقة → يتغير VIN على `ScannedVin`؛ رفض → يبقى القديم. الحالات: قيد الانتظار / موافق عليه / مرفوض.

### ب) تعديل مركبة من اللوحة
- `/Cars/Edit/{id}` يعدّل VIN والمخزن (VinService.UpdateAsync) للأدوار اللي تشوف المركبات.

### ج) سجل تغييرات القطعة
- يظهر بتفاصيل `/Parts/Details` (PartChangeLog) بعد العد أو قبول تعديل كمية — **عرض فقط، مو طلب موافقة**.

إذا تقصدون شاشة موحّدة اسمها «تصحيح البيانات» لكل الحقول: **غير موجود حالياً**.

## 8) مسح VIN

**موجود:** نعم — `POST /api/v1/vins/scan` + اختياري `GET /api/v1/vins/lookup` قبل الحفظ. العرض باللوحة `/Cars`.

### خطوات
1. أحمد يختار مخزن مركبات **9012**.
2. يصوّر ستيكر الزجاج (OCR نص تحت HYUNDAI، **مو** Code128). استخدم أول VIN من `docs/test-barcodes.html` (صيغة تجريبية مثل `KMHCT41D…`).
3. GPS مطلوب وصحيح.
4. **متوقع:** VIN 17 خانة، يحفظ مع المستخدم/المخزن؛ إن كان ضمن المتوقع يظهر الموديل (مثل Elantra/Tucson حسب ملف الجلسة)؛ يظهر بـ `/Cars` وبـ `سجلي`/vins.
5. مسح نفس الرقم ثانية: **409** «رقم VIN ممسوح مسبقًا في هذه الجلسة».
6. حرف I/O/Q أو طول ≠ 17: **400** «يجب أن يتكون رقم VIN من 17 حرفًا ورقمًا (بدون I و O و Q)».

## 9) رفض GPS

**موجود:** نعم — `Validators.GpsError` على: العدّ، مسح VIN، إعادة العد (عبر CountAsync)، طلب إضافة قطعة.

### الشروط اللي ترفض (رسالة عربية واحدة)
`تعذر تحديد موقعك، يرجى المحاولة مرة أخرى` مع **HTTP 400** و**بدون حفظ**:
- lat أو lng ناقص / NaN / Infinity
- lat خارج [-90,90] أو lng خارج [-180,180]
- **الاثنين صفر معاً** `(0,0)`

### خطوات اختبار عملية
1. على قاعدة التجربة، من API بهوية أحمد، أرسل `POST /api/v1/counts` أو `vins/scan` أو `new-part-requests` بإحداثيات `0,0` أو `91,45`.
2. **متوقع:** 400 والرسالة أعلاه؛ القطعة/VIN/الطلب ما ينحفظ.
3. نفس العملية بإحداثيات بغداد الحقيقية → تنجح.
4. لا تعتمد على تزوير GPS بالهاتف الحقيقي إلا لهذا السالب الموثّق؛ الأفضل طلبات API.
